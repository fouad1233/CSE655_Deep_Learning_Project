**Slide 15: the three rules**
- **Convolution: k·k·C_in·C_out.** One filter is a k×k window over all C_in input channels, so it has k·k·C_in weights, and there are C_out filters. The conv layers have no bias, because the BatchNorm after each one adds its own shift.
- **BatchNorm: 2·C.** Each channel learns one scale γ and one shift β. The running mean and variance are averaged during training, not learned, so they don't count as parameters.
- **Linear (fc): C_in·C_out + C_out.** Our age head, 512 → 1, has 512 + 1 = 513.
- **Zero parameters:** ReLU, MaxPool, AvgPool and the ⊕ addition learn nothing.
- **Stride and padding never change the parameter count.** They only change the output size and the MACs.

**Slides 16–19: every layer, one row each.** Each row shows:
- the PyTorch layer name (e.g. `layer2.0.conv1 + bn1`)
- the weight shape, e.g. `[128, 64, 3, 3]`; multiplying its four numbers gives the conv's parameters
- the worked formula: 3·3·64·128 = 9·8,192 = 73,728
- the BatchNorm count: 2·128 = 256
- the row's sum

Each slide ends with a total row and two short "why" notes. For example, layer2's first conv has half the weights of the others because it still receives only 64 channels.

**What 224 really is**
- **It's the standard size of the ImageNet training, not a built-in requirement.** The pretrained weights were trained on 224×224 crops and are evaluated by resizing to 256 and cropping 224. I checked this in torchvision.
- **ResNet18 accepts any input size.** Just before the final linear layer there is an adaptive average pool, which shrinks any feature map to 512×1×1. So the fc layer always gets 512 numbers.
- **The parameter count doesn't change with input size.** I checked: 11,689,512 at 224, 200 and 128 px. The size of a filter doesn't depend on the image, so slides 15–20 are correct at 224 too.

**What does change: the shapes and the compute** (measured, with the 1-output head)

| Input | layer1 | layer2 | layer3 | layer4 | MACs per image |
|---|---|---|---|---|---|
| 224 (ImageNet standard) | 64×56×56 | 128×28×28 | 256×14×14 | 512×7×7 | 1.81 G |
| 200 (UTKFace's own size) | 64×50×50 | 128×25×25 | 256×13×13 | 512×7×7 | 1.56 G |
| 128 (my suggestion) | 64×32×32 | 128×16×16 | 256×8×8 | 512×4×4 | 0.59 G |

**Why I suggested 128**
- **UTKFace images are 200×200.** Using 224 means stretching every image: it adds no information but costs more compute.
- **Compute is the score.** Compute grows with H×W, so 224 costs about 3× as much as 128, in every epoch and every evaluation run. The assignment names "smaller input resolution" as a way to reduce the footprint.

**What 128 might cost**
- The pretrained filters learned faces and objects at 224 scale; at 128 everything looks smaller. Fine-tuning usually adapts, but there's a known accuracy cost when the resolution changes (Touvron et al., NeurIPS 2019, "Fixing the train-test resolution discrepancy").
- The last feature map is 4×4 instead of 7×7, so fine age cues like wrinkles and skin texture could be lost. That might raise the error.

**Why it matters for your grade:** the standard models' MAE is the bar your own CNN must stay within (1.15×). If the baselines run at a size that hurts them, the bar gets easier. That's fair only if all models use the same size and the report explains why.

So the choice is between:
- **224:** the standard size.
- **200:** the native size, no resizing.
- **128:** about 3× less compute than 224, possibly a slightly higher error.

**Slide 10: "224×224 is ImageNet's habit, not a rule of ResNet18"**
- **Where 224 comes from:** ResNet was trained on random 224×224 crops of ImageNet photos. torchvision evaluates the pretrained weights by resizing to 256 and cropping the central 224.
- **The ResNet authors used other sizes too:** for their best result they fed whole images resized to 224, 256, 384, 480 and 640 px into the same trained network. I checked both sentences in the paper itself (He et al., CVPR 2016, §3.4).
- **Which layers care about the size:** a table goes through each layer type. Conv, BatchNorm, ReLU, MaxPool and the average pool all work at any height and width. Only the final linear layer needs a fixed input: exactly 512 numbers.

**Slide 11: how the average pool makes any size work**
- Two drawings at the same scale: a 7×7 map (one channel of layer4's output at 224 px) and a 4×4 map (the same at 128 px). Each map is averaged into one number: 49 values at 224, 16 at 128.
- This happens for all 512 channels, so the final layer always gets 512 numbers.
- The slide quotes the torchvision lines that do this: `AdaptiveAvgPool2d((1, 1))` (line 205) and the end of the forward pass (lines 276–280).
- **Without this pool:** flattening layer4's output would give 25,088 numbers at 224 px but 8,192 at 128 px. The final layer would need a different size for each input, and the pretrained one would not fit.
