## 2.1 How the duplicate check works
A **hash** turns a file's raw bytes into a short "fingerprint". We use MD5, which gives 32 hexadecimal characters. The check works in three steps:
1. Read each JPEG file exactly as stored on disk, without decoding it into pixels.
2. Compute `md5(bytes)` for every file.
3. Group the files by hash. Any group with more than one file is a set of exact copies, so we compare the labels within each group.

Three properties make this reliable, and the new cell demonstrates them on a real pair:
- **Same bytes always give the same hash.** The two files `21_0_2_…659` and `21_0_2_…310` both hash to `009fa4c8…`. Their bytes and their decoded pixels are identical.
- **Changing a single bit changes the hash completely.** Flipping one bit in file A gives `dfe512ea…`, so "almost the same" files don't get similar hashes.
- **Accidental matches are practically impossible.** For 23,703 files the chance of two different files sharing a hash is about 10⁻³⁰. MD5 is unsafe for security, but that doesn't matter for finding copies.

**Limitation:** this only finds copies that are identical byte for byte. A photo that was re-saved or resized has different bytes and a completely different hash. Catching those would need a "perceptual hash" (which compares a tiny blurred version of the image) or comparing image features. We should mention this in the report as a limitation.

## The idea
Every pixel's colour can be split into two parts:
- **Brightness (grey level):** how light or dark the pixel is.
- **Chroma:** what is left after removing the brightness, i.e. *which way* the colour leans (reddish, bluish…).

In a black-and-white photo every pixel leans the same way: not at all for a pure grey photo, or the same sepia direction everywhere for a tinted print. In a colour photo the lean changes from pixel to pixel: skin leans red, the sky leans blue, hair leans brown. **tf measures how much the chroma changes across the image.**

## The formula, step by step
For an image with $N$ pixels, pixel $p$ has values $(R_p, G_p, B_p)$ between 0 and 255.

**1. Brightness of each pixel**, the average of its three channels:
$$g_p = \frac{R_p + G_p + B_p}{3}$$

**2. Chroma of each pixel**, its colour minus its brightness:
$$\mathbf{c}_p = (R_p - g_p,\; G_p - g_p,\; B_p - g_p)$$
This is a 3-number vector that always sums to 0. A grey pixel has $\mathbf{c}_p = (0, 0, 0)$.

**3. The image's tint**, the average chroma over all pixels:
$$\mathbf{t} = \frac{1}{N}\sum_{p} \mathbf{c}_p$$

**4. tf, how far each pixel's chroma is from the tint**, averaged over all pixels and all 3 channels:
$$\text{tf} = \frac{1}{3N}\sum_{p=1}^{N}\sum_{k\in\{R,G,B\}} \big|\, c_{p,k} - t_k \,\big|$$

So tf is the *mean absolute deviation* of the chroma, like a standard deviation but with absolute values instead of squares. Its unit is intensity levels (0–255). Subtracting $\mathbf{t}$ in step 4 is what makes it **ignore the tint**.

## Worked examples (2 pixels each)

**Sepia black-and-white photo.** Pixels (112, 104, 84) and (62, 54, 34):

| | grey level $g$ | chroma $\mathbf{c}$ |
|---|---|---|
| pixel 1 | (112+104+84)/3 = 100 | (12, 4, −16) |
| pixel 2 | (62+54+34)/3 = 50 | (12, 4, −16) |

- Tint $\mathbf{t}$ = (12, 4, −16), and both pixels are exactly that, so **tf = 0** → greyscale ✓.
- The old score mean $|R-G|$ gives |112−104| = 8 → "colour" ✗. That is the bug you spotted.

**Colour photo.** A skin pixel (200, 150, 120) and a blue-sky pixel (90, 130, 200):

| | grey level $g$ | chroma $\mathbf{c}$ |
|---|---|---|
| skin | 156.67 | (43.33, −6.67, −36.67) |
| sky | 140 | (−50, −10, 60) |

- Tint $\mathbf{t}$ = (−3.33, −8.33, 11.67).
- Deviations from the tint: skin (46.67, 1.67, 48.33); sky (46.67, 1.67, 48.33).
- tf = (46.67 + 1.67 + 48.33) × 2 / 6 = **32.2** → colour ✓.

Real images have 40,000 pixels (200×200), but the arithmetic is the same.

## The code in the notebook
```python
a = np.asarray(Image.open(path).convert("RGB"), dtype=np.float32)  # shape (200, 200, 3)
chroma = a - a.mean(axis=-1, keepdims=True)    # step 1+2: subtract each pixel's grey level g_p
tint = chroma.reshape(-1, 3).mean(axis=0)      # step 3: average chroma over all 40,000 pixels
tint_free = np.abs(chroma - tint).mean()       # step 4: mean |c_pk - t_k| over all pixels and channels
```
- `float32`: avoids the wrap-around you'd get with the original 8-bit integers (for example 50 − 100 would become 206).
- `a.mean(axis=-1, keepdims=True)` averages R, G and B for every pixel, keeping shape (200, 200, 1) so it can be subtracted from all 3 channels.
- `reshape(-1, 3)` turns the image into a list of 40,000 pixels, so `.mean(axis=0)` gives the average chroma per channel. That is the tint, a vector of 3 numbers.
- The last line subtracts the tint from every pixel (numpy broadcasts the 3-vector over the whole image) and averages the absolute values over all 40,000 × 3 numbers.

## Why real black-and-white photos score 0–2, not exactly 0
JPEG compression adds small colour noise. It also stores colour at lower resolution than brightness, which creates faint colour fringes at edges. That's why we needed a threshold above 0, and why it was chosen by looking at images.

## Limitations (useful for the exam)
- **Colour photos with very little colour variation**, such as dark faces in dim light or faded old colour prints, can score low. That's the 2–3 grey zone.
- **Black-and-white photos whose tint isn't uniform**, such as a coloured vignette or a hand-tinted print, can score higher.
- **Related published measure:** Hasler & Süsstrunk's colourfulness metric (2003) uses colour differences (R−G and (R+G)/2 − B) and their spread. tf follows the same idea of measuring the *spread* of colour, but removes the mean so a uniform tint doesn't count. ## Why standard models first works well
1. **You learn your target early.** The "acceptable" rule is MAE_own ≤ 1.15 × MAE_best. Until you've trained ResNet18 and MobileNet, you don't know what error your CNN has to reach. With a fine-tuned ResNet18 at, say, 5.5 years, you know your CNN needs about 6.3 or better.
2. **The pipeline gets debugged on models that are known to work.** If a fine-tuned ResNet18 gets a poor error, the bug is almost certainly in the data loading, labels, normalisation or evaluation, not in the model. If you start with your own CNN and get a bad error, you can't tell whether the design or the pipeline is at fault.
3. **You learn the training recipe:** a sensible learning rate, how many epochs before the error stops improving, which loss works (L1 or Huber). That cuts trial and error, and so CO2, on your own CNN later.

## Conditions
**1. Build the shared pipeline first.** Every model needs:
- a fixed train/val/test split saved to a CSV;
- the resized images saved once on disk;
- one dataset loader and one evaluation function (MAE, RMSE, R², error per group);
- the CodeCarbon wrapper, which every run must use;
- the mean/median baseline.

Then a short test on a tiny subset (a few hundred images, 1 epoch, on the CPU), so bugs cost almost no energy.

**2. Use the validation set during development, not the test set.** The rule's MAE_best is a *test* MAE, but if you look at ResNet's test error and then adjust your CNN to beat it, you're tuning on the test set, which the assignment forbids. So:
- During development, compare validation errors only.
- At the end, test each final model exactly once.

**3. "Learn how to modify them," but carefully.** A light, documented tuning of the baselines is fine, for example a small learning-rate search on a subset. Heavy tuning costs CO2, which counts against you. It's also unfair if the baselines get much more tuning effort than your own model, or much less. Report how much tuning each model got.

## Seeds: yes, the same, but there are two kinds
| Seed | Controls | Rule |
|---|---|---|
| **Split seed** | which image goes to train/val/test | used **once**; the split is saved to a CSV that every model reads, so it's identical by construction |
| **Training seed** | weight initialisation (at least the new regression head), shuffling order, augmentation randomness | the same value for every model, e.g. 655 |

Two caveats:
- **The same seed on different hardware doesn't give identical numbers.** CPU, Apple GPU (MPS) and NVIDIA GPU (CUDA) do the arithmetic slightly differently, and some GPU operations aren't exactly repeatable.
- **For the same reason, energy numbers are only comparable on the same machine.** So train all **final** runs on the same machine, ideally the lab RTX 5090, and record the machine in the logs.
- **Optional:** if energy allows, repeat each final model with 3 seeds and report mean ± std. It costs 3× the energy, so maybe only for the final models.

- ImageNet models are pre-trained at 224 px. Fine-tuning them at 64 px usually loses accuracy.

**2. Which models to fine-tune.**
