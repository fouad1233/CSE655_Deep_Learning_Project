No. The only change is the output head, and that change is needed at any input size because we predict one number instead of 1000 classes. I checked by running a 200×200 tensor through both models on the CPU (no training).

**ResNet18 at 200 px.** The formula is H_out = ⌊(H + 2p − k) / s⌋ + 1.

| layer | calculation | output |
|---|---|---|
| conv1 (k7, s2, p3) | ⌊(200+6−7)/2⌋+1 = 99+1 | 64×100×100 |
| maxpool (k3, s2, p1) | ⌊(100+2−3)/2⌋+1 = 49+1 | 64×50×50 |
| layer1 (stride 1) | – | 64×50×50 |
| layer2 (first conv s2) | ⌊(50+2−3)/2⌋+1 | 128×25×25 |
| layer3 | ⌊(25+2−3)/2⌋+1 | 256×13×13 |
| layer4 | ⌊(13+2−3)/2⌋+1 | 512×**7×7** |
| avgpool (AdaptiveAvgPool2d(1)) | averages each 7×7 map | 512×1×1 |
| fc | Linear(512 → **1**) | 1 |

- Every conv, batch-norm and pooling layer works at any H×W, because it slides over the image.
- `AdaptiveAvgPool2d(1)` always outputs 512 numbers, whatever the map size, so `fc` always gets 512 inputs.
- 200 px gives the **same 7×7 final map as 224 px**: the rounding down in layer3 (13 instead of 12.5) makes up for the smaller input. So 200 px is close to what the pretrained network saw. At 128 px the final map would be 4×4.
- Parameters don't change: **11,177,025**, the same number as on your hand-count slides.

**The one code change:**
```python
m = torchvision.models.resnet18(weights="IMAGENET1K_V1")
m.fc = nn.Linear(512, 1)          # was Linear(512, 1000)
```

**MobileNetV3-Large** works the same way: its features give 960×7×7 at 200 px and it also has an adaptive average pool. You replace the last layer, `classifier[3] = nn.Linear(1280, 1)`, instead of `Linear(1280, 1000)`.

**Data side:**
- Skip the usual "resize 256 → crop 224" step and feed the 200×200 images as they are.
- **Keep** the ImageNet normalisation (mean `[0.485, 0.456, 0.406]`, std `[0.229, 0.224, 0.225]`). The pretrained weights expect inputs on that scale.

So 200 px costs you no architecture work.

what shortcut means here

**Assistant:**

A **shortcut** (also called a skip connection) is the second path in a residual block. It carries the block's input around the two 3×3 convs and **adds it to their output**.

```
            ┌──── conv a 3×3 (s2) → BN → ReLU → conv b 3×3 → BN ────┐   main path F(x)
x ──────────┤                                                        (+) → ReLU → output
            └──────────────── shortcut S(x) ─────────────────────────┘
```

**output = ReLU( F(x) + S(x) )**

The convs only have to learn the **change** to the input, F(x). The shortcut passes x itself through.

## Why stage 2 needs a 1×1 stride-2 conv on the shortcut
You can only add two tensors that have exactly the same shape. In stage 2:

- Input **x**: **32 × 50 × 50**
- Main path: conv a, 32→64 with stride 2, gives 64 × 25 × 25; conv b keeps it at **64 × 25 × 25**

So x has the wrong number of channels (32 instead of 64) and the wrong size (50 instead of 25). The shortcut has to fix both:

- **1×1 conv, 32 → 64 channels:** fixes the channel count. Each new channel is a learned weighted sum of the 32 old channels at the same pixel: out[k, i, j] = Σ_c w[k, c] · x[c, i, j]. A 1×1 kernel looks at a single pixel, so it doesn't mix neighbouring pixels.
- **Stride 2:** fixes the size. The kernel is applied only at every second pixel, (0,0), (0,2), (0,4), and so on. Output size = ⌊(50 + 2·0 − 1) / 2⌋ + 1 = **25** (no padding for a 1×1 kernel).

**Hand calculation:**
- Params = 32 · 64 · 1 · 1 = **2,048**, plus BatchNorm 2 · 64 = 128.
- MACs = 25 · 25 · 64 · 32 = **1.28 M**: 625 output pixels × 64 output channels × 32 inputs each.

This is called a **projection shortcut**, option B in the ResNet paper: a 1×1 conv is used only where the shape changes. The paper's option A uses no weights: it skips pixels for the size and pads the extra channels with zeros. Option B is the one torchvision's ResNet18 uses too.

## In stage 1 the shortcut is just x
Stage 1 takes 32 × 50 × 50 in and gives 32 × 50 × 50 out, so the shapes already match. The shortcut is the **identity** S(x) = x: 0 params, 0 MACs, just an addition. That's why the table has no shortcut row for stage 1.

## Why it helps training
For the identity shortcut, the derivative is ∂output/∂x = (1 + ∂F/∂x), ignoring the final ReLU. The "1" is a direct path: the gradient reaches earlier layers even when ∂F/∂x is small. This makes deep networks much easier to optimise, which is the degradation problem we talked about, and usually makes training converge faster.

## Why the receptive field column shows "–" for the shortcut
The shortcut path sees a smaller patch of the image than the main path (its 1×1 kernel adds nothing). The block's receptive field is the larger of the two paths, which is the main path through the 3×3 convs. So the receptive field count in the table follows only the convs.

## User (2026-11-19 17:18)

what "/2" means in 7x7 conv/2 in the figures? I didnt understand

**Assistant:**

"/2" means **stride 2**: the kernel jumps 2 pixels at a time instead of 1, so the output is half as high and half as wide. When there's no "/2", the stride is 1 and the size stays the same, because of the padding.

The output size is H_out = ⌊(H + 2p − k) / s⌋ + 1, where p = padding, k = kernel size and s = stride. For ResNet18's first layer, the "7×7 conv /2" (k = 7, p = 3, s = 2) on the 200 px input:

⌊(200 + 2·3 − 7) / 2⌋ + 1 = ⌊199 / 2⌋ + 1 = 99 + 1 = **100**

So the image goes from 3×200×200 to 64×100×100. That's why the "stem: conv1" label in the diagram shows 64×100×100.

Some examples from your own CNN:

| label in the figure | k, s, p | input → output |
|---|---|---|
| stem: conv, 3×3 conv /2 | 3, 2, 1 | 200 → ⌊(200+2−3)/2⌋+1 = **100** |
| stem: maxpool, 3×3 max /2 | 3, 2, 1 | 100 → ⌊(100+2−3)/2⌋+1 = **50** |
| S1.0 conv1, 3×3 conv (no /2) | 3, 1, 1 | 50 → ⌊(50+2−3)/1⌋+1 = **50** |
| S2.0 conv1, 3×3 conv /2 | 3, 2, 1 | 50 → ⌊(50+2−3)/2⌋+1 = **25** |
| S3.0 conv1, 3×3 conv /2 | 3, 2, 1 | 25 → ⌊(25+2−3)/2⌋+1 = **13** |
| S4.0 conv1, 3×3 conv /2 | 3, 2, 1 | 13 → ⌊(13+2−3)/2⌋+1 = **7** |

Stride 2 matters for three reasons:
- **Compute:** halving H and W means 4× fewer output positions, so each later layer costs 4× fewer MACs. That's why every network in the report uses "/2" layers early.
- **Receptive field:** it doubles the jump j, so every later 3×3 kernel covers twice as many input pixels. In your CNN's table, the RF grows by 8 per conv in stage 1 (j = 4) and by 32 in stage 4 (j = 16).
- **Shortcuts:** the "/2" layers are exactly where a **projection shortcut** is needed. The block's output became half the size, so the input x must also be shrunk by a 1×1 conv /2 before it can be added.

**2. Why these ReLUs are essential (good exam point).** Without them, the whole network would collapse into a single linear layer, however deep it is:
- A conv is a linear map, W₁x.
- Two convs in a row give W₂(W₁x) = (W₂W₁)x, which is again one linear map.
- BatchNorm at inference is just scale + shift, so it's linear too. Global average pooling and the final fc are also linear.

So all 18 conv layers would be worth no more than one conv. ReLU, max(0, z), cuts the network into pieces: it becomes **piecewise linear** with an enormous number of linear regions. That is what lets it map wrinkles, hair and skin texture to an age. The max pool adds a little more non-linearity, but the ReLUs do most of the work.

**3. The shortcuts make it "less linear" in another sense too.** With 8 residual blocks, each block can either pass through its convs F or take only its shortcut. So there are 2⁸ = 256 paths of different depths from the input to the output. The network acts somewhat like an ensemble of shallow and deep sub-networks rather than one straight chain. The zero-init γ we use exploits this: each block starts out as its shortcut, so the untrained network behaves like a shallow one.

## User (2026-11-19 17:33)

why not using gelu etc?

**Assistant:**

ReLU was a deliberate choice for this project, though not one we tested. Here are the reasons and how strong each one is.

**1. It's the cheapest operation.** ReLU is a single comparison, max(0, z), and its backward pass is just a 0/1 mask.
- **GELU** needs x·Φ(x), where Φ is the normal CDF (computed with erf, or with a tanh approximation). Its gradient needs that same function again.
- **SiLU/Swish** (x·sigmoid(x)) needs an exponential.

To be fair, on a GPU these elementwise operations mostly wait on memory, not on arithmetic, so the measured energy difference would probably be small. We didn't measure it, so I wouldn't claim it in the report.

**2. The rest of the design assumes ReLU.**
- **Kaiming init** (He et al.) was derived for ReLU: the gain √2 makes up for ReLU zeroing half of its inputs. With GELU that factor isn't exactly right any more.
- **Conv → BN → ReLU** is the standard, well-tested recipe for residual CNNs. GELU mostly appears together with LayerNorm in transformers and ConvNeXt.

**3. The evidence says the gain would be small for CNNs like ours.** In the ConvNeXt paper (Liu et al., 2022), swapping ReLU for GELU left their ImageNet accuracy unchanged. They kept GELU mainly to stay close to transformers. MobileNetV3 is the exception: it uses hard-swish in its deeper layers, where the authors found it helped, and "hard" means a cheap piecewise-linear version made for mobile CPUs. So even there, the designers chose an approximation to save compute.

**4. A fair comparison with ResNet18.** Your CNN uses exactly ResNet18's block (conv-BN-ReLU), so the only differences are width and depth. Changing the activation as well would add a third difference.

**5. It wasn't our bottleneck.** The first version was *underfitting* (train ≈ val). That's a capacity problem, which more blocks fixed. The activation function wasn't the limiting factor.

**Could you have tested it?** Yes, as a one-change ablation: the same network with GELU instead of ReLU. But that's another ~12 Wh / 5.8 g run for a gain that published results suggest is near zero. We already have the required ablation (basic vs bottleneck), so in a project graded on CO2 it isn't worth it.

The report doesn't currently justify the activation at all, and the assignment asks you to justify each design decision.
